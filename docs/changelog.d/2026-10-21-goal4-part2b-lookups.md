## 2026-10-21 - Lookups and per-record reads read every record; long PDFs are refused, not cut short (Goal 4, part 2b)

The rest of Goal 4 part 2: lookups and per-record reads now go page by page through `src/lib/pagedRead.ts`, with `{ count: 'exact' }`, a fixed sort ending in a unique key, and an error (or a stopped action) instead of a short result. Frontend only, no migration.

- **Statements** (M57): a customer's statement on AR Aging and Customer Detail reads through the new `src/lib/customerStatement.ts`. The statement function's rows have no id, so they are paged in the function's own order and each read is checked two ways: every running balance must equal the sum of the amounts so far, and a read longer than one page must end on the server's current last row. A read that fails a check is tried once more, then shown as an error.
- **Customer Detail** (M27, M64): the recent-transactions card says "the latest 50 of N"; the interaction history reads every interaction, newest first (it kept the newest 50, so its type and outcome filters missed older ones) and shows an error when it cannot load; the financials tab reads every open prepay credit.
- **Orders and deliveries** (M36, M62, and the scheduled-quantity read from N13): an order's field allocations, active fields, field-billing defaults and allocation customers, and the pick list's stock and customer addresses (a failed address read now stops the print); when a scheduled delivery is edited, the quantities other deliveries already claim (a failed read stops the edit instead of allowing too much).
- **Inventory** (M23, M24, M54): a product's ledger and its performer names, a new cycle count's stock and a count's lines, and the Office Cockpit's lapsed crop-program holds with their quote numbers and product names.
- **Jobs and compliance** (N4, N5, N7, N8, N11): the Jobs list's applicator and customer filters (their dispatch and share reads ignored errors; a failure now stops the load), the Dispatch Board and Field View map boundaries, and the license check on a job (a license past the cap read as missing; a failed read now says so).
- **Returns and credit** (N10, L17): the return form's "pick an order", and the credit-limit warning's open-invoice balance (a failed read goes to the existing fail-closed warning instead of counting as zero).
- **Document scanning** (`src/lib/documentOCR.ts`): a PDF over 20 pages is refused before any page is read, with a plain message to split it into files of 20 pages or fewer. It used to scan only the first 20 pages, so an import silently dropped every line after page 20, with only a Sentry warning.

Create Invoice on an order now follows the order's real field split (Sol review): it refuses while the field split details failed to load, and re-counts the order's field allocations on the server just before billing, refusing if that disagrees with the page. Before, a failed allocation read left the page's list empty, so an order split across field owners could be billed as one invoice to the order's customer (`create_invoice_from_order` does not check allocations). Test: `src/pages/OrderDetail.invoiceSplitGate.test.tsx` (both refusal cases fail with the check removed).

A failed read on the Jobs list now also clears the list (it left the previous, differently filtered jobs on screen), and the inventory ledger clears the last product's rows when the next product opens, so a failed read never shows them under the wrong name.

Tests: seven new `*.paging.test.*` files (credit limit, statement module, AR Aging statement, interaction history, inventory ledger, the return form's order picker, the Jobs applicator filter) use 1,005 or 1,205 rows against the 1,000-row fake server. Run against the old code, every one of their screen tests failed (the statement module is new, so its screen-level test stands in); all pass now. The 20-page scan test uses a 21-page PDF. Three existing tests whose fakes answered without paging (`TransactionLedgerModal.test.ts` and the two Cycle Counts race tests) now answer `.range` with a count.

Live check on 2026-10-21 with a temporary 10-row page (local app, live database, read-only): a product's ledger 34 transactions (database 34, four pages); a cycle count's lines 83 (database 83, nine pages); the return form's order picker for one customer 6 orders, newest first (database 6); a 21-line order's page and a customer's 90-day statement loaded with no error. Live statements are at most a few rows, so the multi-page statement path is proven by the tests only.
