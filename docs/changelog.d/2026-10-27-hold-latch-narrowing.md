## 2026-10-27 - The hold latch ignores machine text and holds one session at a time

- Narrowed under the guard-cleanup exception (Mason, 2026-10-27: "dont close holes i want loooser guards"). What still enforces the rule: Mason's own typed "stop", "pause" or "hold on" still latches the hold and still hard-blocks pushes, merges, PR publishing, migration applies, deploys and live SQL writes in that session.
- A CI or Auto-fix notice (`<ci-monitor-event>`) sent as its own message is machine text and never latches; inside a longer message it is stripped, so Mason's "stop" beside it still latches. A subagent report that reaches the hook as `<agent-message from="…">` plus the harness's exact frame line, with no "Another Claude session sent a message:" line, is now recognised; two such reports latched holds on 2026-10-27 (replayed before and after the fix).
- Every "stop", "pause" or "hold on" Mason types still latches, however it is phrased. Guessing which uses were only descriptive was tried in this PR and dropped (Mason, 2026-10-27), because each rule kept missing new wordings.
- Each session now keeps its own hold file (`.claude/session-state/hold-<session_id>.json`; an unusual id is hashed into `hold.<hash>.json`, and `hold.json` is used only when the id is missing, null or empty), and a session's guard reads only its own, so one session's stop or misfire no longer freezes every session that runs hooks from the main checkout (hook calls that carry no session id still share the one fallback file).
