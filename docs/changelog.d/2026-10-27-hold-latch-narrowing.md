## 2026-10-27 - The hold latch misfires less and holds one session at a time

- Narrowed under the guard-cleanup exception (Mason, 2026-10-27: "dont close holes i want loooser guards"). What still enforces the rule: Mason's own typed "stop", "pause" or "hold on" still latches the hold and still hard-blocks pushes, merges, PR publishing, migration applies, deploys and live SQL writes in that session.
- CI and Auto-fix notices (`<ci-monitor-event>`) are machine text and never latch. A subagent report that reaches the hook as `<agent-message from="…">` plus the harness's exact frame line, with no "Another Claude session sent a message:" line, is now recognised; two such reports latched holds on 2026-10-27 (replayed before and after the fix).
- "stop" or "pause" used as an ordinary word no longer latches: "make the gate stop refusing", "the hook should pause retrying", and Mason's real 2026-10-27 message "set ENABLE_COMMIT_REVIEW=0 in my user settings to stop the per-commit security reviews", which had blocked a merge.
- Each session now keeps its own hold file (`.claude/session-state/hold-<session_id>.json`, `hold.json` only when no session id arrives), and a session's guard reads only its own, so one session's stop or misfire no longer freezes every session that runs hooks from the main checkout.
