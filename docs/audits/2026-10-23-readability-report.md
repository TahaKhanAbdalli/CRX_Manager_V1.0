# Readability report: the 10 hardest places to follow in CRX Manager

**Date:** 2026-10-23 · **Code read at:** `main` @ `f52fbea6b` · **Scope:** read-only; no code changed.
**Audience:** the senior developer taking over in December 2026.

## Why this exists, and how to use it

CRX Manager becomes the only billing system on **2027-01-01**. Mason decided not to run a broad
simplification before then, because rewriting money screens risks real invoices. This report is a
map, not a work order. Use it to get your bearings now, and to choose what to simplify **after the
January pilot is stable**.

Each item gives where it is, what makes it hard, how risky a change would be, and a suggested
simplification with a rough size: **S** under a day, **M** 1–3 days, **L** more than 3 days. The
ranking weighs two things together: how much the item slows a newcomer down, and how safe it is
to fix. A very confusing area that is also dangerous to touch ranks below one that is nearly as
confusing and safe.

**Method.** The Graphify architecture graph (built from `f52fbea6`: 13,701 nodes, 28,463 edges)
picked the most-connected modules. Its top hubs are `useToast`, `assertRpcResult`, `useAuth`,
`supabase`, `sanitizeError`, `useIdempotencyKey`, `fetchAllRows`, `checkMutationResult` and
`logActivity`. Four focused source reviews followed, one per area. Every finding below was
re-checked by opening the cited lines. Line numbers are correct at `f52fbea6b` and will drift. A
separate session is removing dead code at the same time, so some cited lines may move or
disappear.

**Size of the codebase (non-test `src/`):** about 188K lines, 15.5K of them generated

## The ranked 10

### 1. You cannot easily find the current version of a database function

- **Where:** `supabase/migrations/` (971 files) and `docs/reference/rpc-functions.md`.
- **What makes it hard:**
  - The live body of an RPC is whichever migration redefined it last. Count of migration files
    that redefine each function:

    | Function | Files |
    |---|---|
    | `complete_delivery` | 38 |
    | `save_quote` | 28 |
    | `void_invoice` | 23 |
    | `convert_quote_to_order` | 22 |

  - Many RPCs are thin wrappers around dated `_…_impl` functions (about 95 of them). Example: the
    newest `save_quote` file, `20261019010000_cost_margin_admin_only_rpc_leaks.sql`, only wraps
    and calls `_save_quote_below_cost_impl_20260810`. The real body is in a different, older file.
  - The schema baseline is Brotli-compressed (`supabase/baselines/*.sql.br`), so it cannot be
    searched, and it is frozen at 2026-07-27.
  - Some `COMMENT ON FUNCTION` bodies are single paragraphs of about 5,000 characters. See
    `save_job` in `20260904185900_refuse_null_job_field_acres.sql:1611`.
  - `rpc-functions.md` says its own counts were last measured 2026-08-11.
- **Risk of fixing:** none at runtime. This is a generated document, not a code change.
- **Simplify:**
  - Generate a committed index: function → newest migration → the `_impl` chain it calls.
  - Better still, add a decompressed, per-function dump of the live schema (for example
    `schema/current/<function>.sql`), regenerated by CI after each apply.
  - Size **M**. This is the single biggest onboarding win.

### 2. The tier-price and line-total math has several copies that disagree

- **Where:**
  - `src/lib/quoteCalc.ts:41-58`
  - `src/pages/QuoteBuilder.tsx:1432-1527`
  - `src/pages/OrderDetail.tsx:583-588` and `:2253-2260`
  - `src/pages/NewOrder.tsx:321`
  - `src/components/deliveries/QuickDeliveryModal.tsx:313`
- **What makes it hard:**
  - The fallback from a tier price to the tier-1 price is written about 7 times, with 3 meanings:
    - `getTierPrice` uses `||`, so a stated **$0** tier-2/3 price falls back to tier 1.
    - `getStatedTierPriceCents` uses `??`, so the $0 is kept.
    - SQL uses `COALESCE(tier2_price, tier1_price, 0)`, which also keeps the $0.
  - The **unit-tested** `quoteCalc.recalcItem` ignores `price_override` (`quoteCalc.ts:76`). The
    copy QuoteBuilder actually runs honours it (`QuoteBuilder.tsx:1460`). So the tests cover a
    copy the screen does not use.
  - Wrong comments add to the confusion:
    - `OrderDetail.tsx:583` says "Cascade: tier3 → tier2 → tier1". Both this code and
      `getTierPrice` go tier3 → tier1 and skip tier 2.
    - The `quoteCalc.ts` header says the module is "NOT imported" by screens, but
      `InvoiceDetail.tsx` and `JobDetail.tsx` import it.
- **Risk of fixing:** **money.** A price preview can differ from what the server stores. The
  server recomputes quote totals in a trigger, so stored totals are safe. Invoice line prices,
  however, are seeded from `getTierPrice` (`InvoiceDetail.tsx:921`).
- **Simplify:**
  - Write one `tierPriceCents(product, tier)` that matches the SQL, and delete the copies.
  - Point QuoteBuilder at `quoteCalc.recalcItem`, after adding `price_override` to it and to its
    tests.
  - Size **S–M**.
  - **Blocked on a business decision:** whether a stated $0 tier price is real. This is open with
    Mason.

### 3. Money formatting and conversion skip the shared helpers

- **Where:** across `src/`. The shared helpers are in `src/lib/money.ts` and
  `src/lib/parseCents.ts`.
- **What makes it hard:**
  - `money.ts:17` says "Do NOT re-alias these to a local `fmt`". Yet 39 files import
    `formatCents as fmt` or `formatUSD as fmt`. So `fmt` takes **cents** in `InvoiceDetail.tsx:25`
    and **dollars** in `OrderDetail.tsx:29`, and you must check the import every time.
  - Pages divide cents by 100 and then format the result as dollars, for example
    `OrderDetail.tsx:1305-1308` and `:1985`.
  - There are about 78 `toFixed(2)` calls, about 56 `Math.round(x*100)` calls, and 18 currency
    formatters built inline.
  - `centsTimesQuantity` (`money.ts:194`) is the helper that rounds exactly like the database's
    `safe_cents_qty`. Only `JobDetail.tsx` uses it. Elsewhere, cents × quantity is computed in
    floating point (`InvoiceDetail.tsx:1003`, `QuickDeliveryModal.tsx:359`).
  - Two helpers with near-identical names behave differently:
    - The local `dollarsToCents` in `FieldAppSplitInvoiceEditor.tsx:137` keeps the minus sign.
    - The shared `parseDollarsToCents` strips it.
  - Background: the schema itself is split. Products, orders and quotes store **dollars**;
    invoices and jobs store `*_cents`.
- **Risk of fixing:** mostly display only, so low. The exceptions are the places that compute an
  amount which is then saved; see item 10.
- **Simplify:**
  - Replace every `fmt` alias with the helper's explicit name.
  - Add the lint rule that `money.ts` already proposes.
  - Send cents × quantity through `centsTimesQuantity`.
  - Size **M**. It is mechanical, but a money PR, so it needs a CodeRabbit review under the
    current rules.

### 4. Status badges and status groups are redefined page by page, and disagree

- **Where:**
  - The same 7-entry `statusBadge` map: `src/pages/InvoiceDetail.tsx:86-98`,
    `src/pages/Invoices.tsx:69-81` and `src/components/field-invoices/FieldInvoicesListPanel.tsx:56-68`.
  - The shared map these pages bypass: `src/components/ui/Badge.tsx:38-71`
    (`statusToBadgeVariant`).
- **What makes it hard:** the same status shows in different colours:

  | Status | Page copy | Shared map | Invoice PDF (`invoicePdf.ts:514`) |
  |---|---|---|---|
  | paid | blue | green | green |
  | posted | green | green | blue |
  | cancelled | grey | red | — |

  - Status *groups* are also typed out inline in about 10 places, for example
    `['draft','unposted']` and `'scheduled','in_progress'`.
  - `invoices.status` has both `draft`/`unposted` and `voided`/`cancelled`, and no comment says
    how each pair differs.
  - There is no transition table in TypeScript. Transitions live only in SQL triggers and RPCs,
    which is correct, but nothing tells you that.
- **Risk of fixing:** low. These are display and filter lists, with no money logic.
- **Simplify:**
  - One `<StatusBadge kind="invoice" status=…>` component that reads `Badge.tsx`.
  - A `src/lib/statusGroups.ts` with typed sets and a one-line meaning for each status.
  - Size **S**.

### 6. DeliveryDetail resets itself by hand because its route is not keyed

- **Where:**
  - `src/appPages.tsx:165` (`<DeliveryDetail />` with no key)
  - `src/pages/DeliveryDetail.tsx:102-145` and `:205-225`
- **What makes it hard:**
  - Jobs are keyed by id through `JobDetailRoute` (`appPages.tsx:200`), so the job page remounts
    on navigation. Deliveries are not. So DeliveryDetail resets *some* state in two
    `useLayoutEffect`s.
  - Those effects do not reset `editing`, `editItems`, `remainders`, `relatedInvoices` and a few
    others.
  - `signatureRouteIdRef` started as a signature guard. It is now the general "am I still on this
    delivery?" test for every load and action.
  - The completion form is written twice, once in the driver layout and once in the office
    layout (`:1841-1940` vs `:2662-2800`). The two copies have already drifted.
  - So is the receipt email HTML (`:1297-1358` vs `:1437-1480`). See "Bugs spotted" below.
- **Risk of fixing:** low for the key. Delivery completion touches inventory, but the key change
  does not alter what is saved.
- **Simplify:**
  - Key the route by id, as jobs do, then delete the two reset effects and most of the route-ref
    checks. Size **S**.

### 7. JobDetail.tsx: about 110 pieces of state and a 680-line save chain

- **Where:** `src/pages/JobDetail.tsx` (5,427 lines).
- **What makes it hard:**
  - About 110 `useState`, including 15 modal booleans and about 17 "in progress" flags. State is
    declared in two separate places (`:305-538` and `:1310-1427`).
  - Dirty tracking copies the whole form into a snapshot and keeps a dependency list by hand
    (`:1430-1437`, `:1697-1714`).
  - Three refs guard against stale loads. The file's own comment (`:2128-2153`) says most of
    this is "Redundant while the route stays keyed", and it is keyed.
  - Saving runs through `handleSave` → `handleOverrideConfirm` → `runJobSave` → `performSave` →
    `assignWithOverride` (`:2491-3172`). The chemical-line checks run twice on the way.
  - `chemRowDefects` (`:1562-1685`) re-implements the SQL refusals of `save_job`. The SQL is the
    authority. The copy has to be updated by hand each time a refusal is added, and no test checks
    that the two still match.
  - The pre- and post-notification senders (`:590-767`, `:769-924`) are about 150-line
    near-copies.
  - Naming: `ChemRow.driver` means "which field the operator typed (rate or quantity)". Everywhere
    else in the app, "driver" means a delivery driver.
  - Cancel is a raw table update (`:3276-3289`), while start, complete and transfer use RPCs. A
    SQL trigger still enforces the rule.
- **Risk of fixing:** medium. The Chemicals tab and the save chain touch money (job pricing,
  invoicing) and inventory.
- **Simplify, in this order:**
  1. Merge the two notification senders. Size **S**, no money.
  2. Delete the guards the code itself calls redundant. Size **S–M**.
  3. Split the tabs into components: Locations `:4183`, Chemicals `:4447`, Loader `:4697`,
     Notifications `:4979`. Replace the 15 modal booleans with one `openModal` value. Size **L**.
  4. One `validateJobSave()` that returns a list of problems, plus one `saveJob()`. Size **M**,
     money.

### 8. QuoteBuilder.tsx: a hidden state machine in about 30 refs

- **Where:** `src/pages/QuoteBuilder.tsx` (5,466 lines; one component from `:261`).
- **What makes it hard:**
  - Hooks: 82 `useState`, 31 `useRef`, 13 `useIdempotencyKey`, and 14 modals in about 1,775
    lines of JSX (`:3691-5466`).
  - The row-version token, the recovery latches and the "reset after reload" flags all live in
    refs (`:311-387`, `:911-1004`). React never re-renders on them, so you have to trace an
    unwritten state machine by hand.
  - Dirty tracking is an effect that copies state into state, gated by three flags
    (`:701-718`).
  - Convert-to-order is run from the browser and is not atomic (`:3369-3615`):
    1. a client pre-check that duplicates the server's `BOOKING_PARTIALLY_DRAWN` refusal;
    2. `saveQuote('accepted')`;
    3. the `convert_quote_to_order` RPC;
    4. if that fails, a "compensating" status write straight to the table (`:3595`).
  - The button rules `canCancel`, `canDecline` and `canRevert` (`:629-670`) copy SQL rules by
    hand.
  - The pricing-math copy is covered in item 2.
- **Risk of fixing:** **high.** Quotes feed orders, inventory draws and commission. Convert is
  quote-to-cash.
- **Simplify:**
  - Split the render into `<QuoteSectionsEditor>`, `<DrawDownModal>` and
    `<VersionHistoryModal>`. Size **M**, no money logic.
  - Extract `useQuoteRowVersion` and `useQuoteDirtyTracking` hooks. Size **M**.
  - Later, move the convert pre-check and the revert into the RPC, so convert is a single atomic
    call. Size **L**, needs a migration.

### 9. FieldApplicationInvoice.tsx: a save made of several writes, and void one member at a time

- **Where:** `src/pages/FieldApplicationInvoice.tsx` (4,171 lines).
- **What makes it hard:**
  - `performSave` (`:1843-2216`) makes 4 to 6 separate writes from the browser, in this order:
    1. `save_field_app_invoice`
    2. an activity insert
    3. `update_field_app_applied_info`
    4. an `invoices` read
    5. `update_field_app_invoice_billing`, once per key
  - Partial failures are tracked with `appliedInfoOk` and `billingOk` flags, so you have to reason
    about every half-done state.
  - Post and unpost of a split group are atomic RPCs (`post_invoice_group`,
    `unpost_invoice_group`). Void is a JavaScript loop over `void_invoice` (`:2366-2386`), so a
    group can end up half-voided. The comment at `:268-270` admits there is no group RPC.
  - Four idempotency-key strategies sit in one file:
    - `useIdempotencyKey`
    - a hand-rolled `recordSend`/`UnansweredKey` receipt protocol (`:178-215`)
    - `unpostKeysRef`/`voidKeysRef` maps
    - `billingKeysRef`
  - The payment-terms parsing is copied twice in this file (`:1095`, `:2518`) and once more in
    `InvoiceDetail.tsx:578`. It mirrors SQL `parse_payment_terms_days`.
  - The JSX is about 1,260 lines, across 5 tabs and 7 modals.
- **Risk of fixing:** **high.** Posting, voiding and billing splits are money, and the atomic
  fixes need migrations.
- **Simplify:**
  - A `void_invoice_group` RPC, so void matches post and unpost. Size **M**, migration.
  - One `paymentTermsDays()` helper. Size **S**.
  - One idempotency approach for the whole file. Size **M**.
  - Fold the follow-up writes into the save RPC. Size **L**, migration.
  - Split one component per tab. Size **M**.

## What is good: keep these patterns

These work, are tested, and are used widely. Simplify *toward* them; do not rewrite them.

- **`src/lib/db.ts`:** the one Supabase client, `assertRpcResult` (used in about 123 files),
  `checkMutationResult`, and typed `RpcErrorCodes` with `hasRpcCode`. This is the backbone of
  error handling.
- **`useIdempotencyKey`** (`src/hooks/useIdempotencyKey.ts`): small, and its header explains
  receipt semantics well. Every mutating RPC takes a key, and the SQL side enforces it. Do not
  remove keys while simplifying a page.
- **The SQL is the authority for money and inventory.** Triggers recompute quote line totals;
  `save_job` derives job totals; posting and inventory moves are RPCs. When a React copy of a
  rule disagrees with SQL, SQL wins. Delete the React copy or make it display-only; never move the
  rule *out* of SQL.
- **`src/lib/money.ts` and `src/lib/parseCents.ts`:** exact integer-cents parsing that refuses
  fractional cents, and a `centsTimesQuantity` that matches the database. The problem is that
  pages bypass them, not the helpers themselves.
- **`src/appPages.tsx`:** one page list drives the router, the permission registry and the
  sidebar, and `routeBaseline.test.tsx` proves access. Two field-app routes are still in
  `App.tsx:125-126`; fold them in.
- **Already-extracted, tested helpers:** `chemCalculator`, `jobSaveHelpers`, `loaderWorksheet`,
  `deliveryEvidence`, `paperTicket`, `deliveryEditItems`, `inventoryShortage`,
  `commissionSplitConcurrency`, `quoteLifecycleRpc`, `quotePdf`. Extracting more like these is
  the right direction for the big pages.
- **`fetchAllRows` / `fetchAllRowsForIds`** (`src/lib/pagedRead.ts`), **`runCriticalAction`**,
  **`useUnsavedChanges`**, **`useLatestRef`**, **`src/lib/sentry.ts`** and
  **`dateUtils.todayInBusinessTz`** (Chicago business date). All are small, clear and widely
  used.
- **`FieldApplicationInvoice.tsx` money derivation** (`:894-972`): values are derived with
  `useMemo` in integer cents rather than stored in state. Copy this pattern into the other pages.
- **The guard and hook system** under `.claude/hooks/`: it is heavy, but it enforces the money,
  migration and review rules in code. Read `docs/reference/agent-guardrails.md` before changing
  it.

## Suggested order after the pilot

1. Item 1, the function index. It has no runtime risk and makes every later item faster.
2. The quick wins, B1–B4 first.
3. Items 4 and 5 (statuses and comments), alongside other work.
4. Item 2 (tier pricing), once Mason decides the $0-tier question. Then item 3.
5. Items 6–10, one page at a time. Extract hooks and components before changing any money flow,
   and move non-atomic money flows into RPCs as separate, migration-reviewed PRs.
