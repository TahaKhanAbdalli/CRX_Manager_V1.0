# Backup health alert: design (Goal 6, agent step 3)

**Status:** design only, 2026-10-19. Nothing is built. Building it needs changes in the private repo
`masonwells1/CRX_Backups` and possibly a new secret there; adding a secret is Mason's gated action.

## Problem (from `docs/plans/2026-10-18-goal-6-safety-net-findings.md`)

- The only failure signal is a GitHub email. Nobody is named to act on it.
- The Sunday workflow fails only when the dump is under 10 KB. A truncated dump over 10 KB passes.
- A run that never starts (GitHub disabled a scheduled workflow, or the schedule was skipped) produces no failure and no email at all.
- The 2026-08-30 scheduled run failed and the next dump was 10 days later.

## What should be true

1. A backup that is **bad** is a failed run: the workflow fails and says why.
2. A backup that is **missing** is noticed: someone is told within one day of the expected time.
3. Mason sees it where he already looks, in plain words, with one next step.

## Design

**A. Stronger check inside the Sunday run (in `CRX_Backups`).**
- Compare the new dump size to the previous dump. A drop of more than 30% is a **warning** that forces the restore and row-count checks below to be reviewed, not an automatic failure: legitimate cleanups or deletions can shrink a dump, and a hard size rule could reject good dumps and leave the off-site backup stale. The hard failures are an unreadable archive and a shrunken append-only table.
- Prove the **whole** archive is readable, not just its table of contents (`pg_restore --list` reads only the contents list, so a dump cut off after it would pass). Restore the decrypted dump into a disposable Postgres inside the workflow run (a service container that is thrown away). That container must match Supabase, or every good dump would fail: use a pinned Supabase-compatible PostgreSQL image, create the roles and schemas the dump references, and enable the non-default extensions first (PostGIS for `fields.centroid` and `fields.boundary`, plus the others the migrations require; Supabase's logical-restore guide lists the procedure). Fail on any *data* error (COPY failures, missing data), and fail if the restored table set does not match the schema expected by that dump's own migration ledger. Also verify that all three archive sections restored (pre-data, data and **post-data**): compare the restored indexes, constraints, triggers, functions, policies, **row-level security switches and grants** (policy names alone prove nothing, because PostgreSQL keeps a table's policies even when row-level security is off; see `supabase/baselines/README.md`, the `relations_and_acl` row: also compare each table's `ENABLE ROW LEVEL SECURITY` and `FORCE ROW LEVEL SECURITY` flags, the grants on every table, column, sequence and function, and the default privileges in `pg_default_acl`, which decide what the next new object gets), views (including each view's security settings, for example `profile_public_view`) and **sequences** (for each expected sequence, such as `invoice_number_seq` feeding `invoices.invoice_number`, work out the number it will hand out next, which is its `last_value` if `is_called` is false and otherwise `last_value` plus its increment, and confirm that next number is higher than the highest number already stored with that sequence's prefix, for example `INV-2026-0042` counts as 42, so the first new invoice after a restore cannot collide; do not require `last_value` itself to be higher, because a correctly restored sequence that has already handed out its last number has `is_called` true and `last_value` equal to that number) against an **independent** expected schema (a schema-only capture taken from the same exported snapshot and saved beside the dump, or the repository migrations rebuilt up to the dump's ledger version in a scratch database), never against the archive's own contents list, which would omit the same objects if the section were missing. Fail on any missing or different one, and write no success marker until this check passes. A dump without its post-data section can restore every table and row while lacking the triggers and constraints that enforce the money and inventory rules, and the ledger would still claim those migrations ran. Do not compare the table count with the previous run: an approved migration that drops or consolidates a table would then fail every later dump and leave the backup looking late forever. An explicit reviewed baseline rollover is the only way the expected table set changes. Row counts are checked only where a drop is not a normal event: **append-only tables** (for example `inventory_transactions`) must not shrink. Tables where deletes are allowed (`customers`, `orders`, and `invoices`, where `delete_invoices` and soft deletes exist) get a warning, not a failure, when the count drops by more than 5% since the last run, and the baseline records whether `invoices` counts include soft-deleted rows. Which tables are append-only is confirmed against the delete rules when this is built. The disposable restore must also prove the **Auth data** is in the dump: whether `auth.users` (and the related Auth tables) are included is unverified today, so the check fails unless `auth.users` is present and non-empty, its count dropping since the last run is a warning (legitimate user deletions happen), not a failure, unless it falls to zero, and every `profiles` row has a matching login. A dump without logins cannot restore existing users, so it is not valid. Do not trust counts taken only from the restored copy, because an archive that silently omits rows would then be compared with itself. Capture the key-table counts from the live database inside the same snapshot as the dump (open one session, export its snapshot with `pg_export_snapshot()`, keep that session open, and run both `pg_dump --snapshot=<id>` and the count queries against that same exported snapshot; the exporting session uses `REPEATABLE READ` and stays open, and the count session starts `BEGIN ISOLATION LEVEL REPEATABLE READ` and runs `SET TRANSACTION SNAPSHOT '<id>'` before its first query, because the default `READ COMMITTED` level would take a fresh view for each query; a query merely "in the same run" is a different view and normal writes between the two would make a good dump fail), write them to the baseline file bound to that archive's name and checksum, and fail when the restored counts differ from those same-snapshot counts for **every** table the source database holds data in, mutable ones included, except the `cron` scheduled-job tables, which the restore deliberately leaves out: those form a separate class that must be empty after the restore and are not compared with source counts. Take that table list **independently from the source database** inside the same exported snapshot (never from the archive's own contents list), and require both an archive data entry and a matching restored count for each one before any success marker is written, so a dump that silently drops a table's data (for example `invoice_items`) fails: both counts come from one consistent snapshot, so any difference means the archive lost rows. The 5% warning rule applies only to the separate comparison with the previous week's baseline (legitimate deletes between backups), never to this restore-versus-source check.
- Record row counts for a fixed list of key tables (`customers`, `invoices`, `orders`, `inventory_transactions`, `allocation_sets`, `prepay_credits`, plus `auth.users`, `profiles` and any other Auth table a restore needs; the exact restored-versus-source match applies to every one of them, while the week-over-week user-count drop stays a warning) into a small `baseline-YYYY-MM-DD.json` committed beside the dump. The restore drill compares to this file (draft restore procedure `docs/plans/2026-10-19-goal6-restore-procedure-draft.md`, step 5, which uses a live-count fallback until this exists).

**B. A separate missed-run watchdog (not the backup job itself).** A job that does not depend on the Sunday workflow running:
- Runs daily at **10:00 UTC** (two hours after the Sunday 08:00 UTC backup is due). Freshness comes from the **validated success marker**, not a file's commit time: the marker records the dump's capture time, file name and checksum, and the watchdog checks that the marker matches the newest dump and that the capture time is on or after the due time. Re-committing an old dump therefore cannot make it look current. The commit timestamp of the newest file in `CRX_Backups/backups/` is only a cross-check.
- It compares that timestamp with the **most recent due time**: the latest Sunday 08:00 UTC at or before now (today, if today is Sunday). It raises the alert when no validated marker shows a dump captured at or after that due time. A missed Sunday run is therefore flagged at 10:00 UTC the same Sunday, inside the one-day target; a normal run (captured shortly after 08:00) passes, and a run more than two hours late is flagged, which is intended.
- Home options, in order of preference: (1) a scheduler **outside GitHub Actions**, such as the existing nightly watchdog or a scheduled task on a machine or service we control, that reads the newest backup date from `CRX_Backups` and raises the alert. This is preferred because if Actions is disabled for the repository or organization, no workflow in it runs, so a second workflow cannot detect that failure. (2) A second scheduled workflow in `CRX_Backups` that only reports "Backup is late" in its own run summary (and the email or text channel); it never creates the issue, which only the outside watchdog writes. It is an additional layer only. The outside scheduler needs read access to `CRX_Backups` (a credential Mason must approve); the in-repo workflow needs no new secret.

**Credentials for B.** Reading the newest backup date needs only read access, but creating and assigning an issue needs Issues **write** permission on `CRX_Backups` (GitHub's create-issue API requires it). Either approve a separate least-privilege token limited to Issues write on that one repository (Mason's approval; stored only in the scheduler), or send the alert through an independent channel that needs no GitHub write access, such as an email or text sent by the scheduler itself. A watchdog that can detect a missed backup but cannot deliver the alert does not meet the one-day target.

**Rules that keep the alert trustworthy.**
- **A dump counts as current only after validation.** The Sunday workflow commits the dump and its baseline file only after the restore and row-count checks pass, and in every case also writes a success marker tied to that exact dump file (name, checksum and capture time); the watchdog must find that marker before treating the dump as current, and a commit alone is never proof. A dump that exists but failed validation is not current, so it cannot silence the late alert.
- **One open alert, not many.** Before creating anything, the watchdog searches for an existing open "Backup is late" issue and reuses it, adding a comment rather than a new issue or a new notification. The issue stays open while backups remain unvalidated and is closed only after a validated new dump is detected.
- **One issue writer.** Only the outside watchdog creates or updates the "Backup is late" issue. The optional in-repository workflow never creates issues; it only reports in its own run summary and sends the email. A search-then-create sequence cannot guarantee one open issue when two writers run at once, so there is exactly one writer (or, if a second is ever added, a shared lock or a fixed issue key that makes creation idempotent).
- **Handoff from the Sunday workflow to the outside scheduler.** The Sunday workflow does not need to call the scheduler. On a validation failure it simply does not commit the dump (or marker), and the scheduler's daily check finds no validated dump and alerts. Optionally it also sends its own email directly (a signed message to the same address or text number), so a failure is reported within minutes rather than at the next 10:00 UTC check. If Actions is disabled it sends nothing, which is why the scheduler check is the primary path.
- **Mutable-table list is not exhaustive.** Beyond `customers`, `orders` and `invoices`, `allocation_sets` and `prepay_credits` are also mutable (admins can delete from both). The rule is derived from the delete rules, not from this list: any table someone can delete from gets a warning, not a failure, on a drop.
- **One delivery contract for A and B.** The Sunday workflow (A) and the watchdog (B) both alert through the same channel: an independent email or text sent by an outside scheduler, plus the GitHub issue (assigned to Mason) when an Issues-write token has been approved. The Sunday workflow never writes the issue (see "One issue writer"): its failure alert is its own run summary and the email or text through the outside channel, and the outside watchdog is the only writer of the GitHub issue, using the approved token and channel above. If Actions is disabled the Sunday workflow alerts nothing, which is exactly why the watchdog must be external.

**C. Where Mason sees it.** Both A and B end in the same place: a GitHub issue in `CRX_Backups` (the outside watchdog **assigns the issue to Mason and mentions him by username**, and once the recovery owner and backup person are named (runbook 4.2) assigns or mentions both of them too; until then Mason is the required primary responder, because GitHub emails only people who are watching, assigned or mentioned, not merely the repo owner; the build step must also confirm Mason's GitHub notification settings send email for `CRX_Backups`, or add a second channel such as a text or email sent by a scheduled task), plus a line in the app's admin health view if one exists when this is built. The alert text is plain: "The weekly backup did not finish. Last good copy: <date>. Next step: tell your agent to check the backup."

**D. Who responds.** The recovery owner and backup person (runbook 4.2) once Mason names them. Until then, Mason.

## Not covered by this design

- File (Storage) backups: separate step; the same watchdog pattern applies once they exist, using the manifest comparison.
- Alerts for PITR (Supabase dashboard); revisit after the Pro upgrade.

## Build checklist (when approved)

1. Edit `.github/workflows/offsite-backup.yml` in `CRX_Backups`: size-ratio check, disposable-restore check, baseline file.
2. Add the **external** lateness check (a scheduler outside GitHub Actions that reads the newest backup date from `CRX_Backups`, using a read-only credential Mason approves). This is required, not optional: if Actions is disabled, nothing inside it can notice. Add the in-repository daily lateness workflow (no new secret) only as a second layer.
3. Prove it: run with deliberately damaged test dumps on a branch and watch each fail: one cut off before the end of the table of contents, and one cut off **after** it (intact contents, missing data blocks); run the lateness check against a faked old date and watch the issue open. Do not merge on "it looks right".
4. Update runbook 4.11 and the findings note.
